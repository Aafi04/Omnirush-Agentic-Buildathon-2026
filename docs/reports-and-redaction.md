# Investigation reports and sensitive-data boundary

## Data flow and trust

1. The bounded importer validates original JSONL in memory (unchanged event schema
   1.0, limits and six-rule semantics).
2. The deterministic engine evaluates original values under baseline/strict 2.0.
3. `public_analysis()` collects recognized sensitive values, then sanitizes every
   public analysis surface, including payloads, excerpts, config, tool names,
   identifiers, policy sources and rule explanations. There is no raw-analysis API.
4. Both exports are generated from that sanitized analysis. The frontend downloads
   **only** backend `reports.json` / `reports.markdown` strings in typed Blobs, not
   a serialization of the response or the imported file.

The engine's internal raw goldens are still useful detector regression tests; they
are not public reports. `/api/samples/*` serves the original public synthetic demo
input so it can be imported. It contains no real credentials. Nothing imported is
executed, fetched, persisted automatically or logged. Report downloads are explicit.

The browser receives sanitized events for inspection. Filenames from imports and
arbitrary network/File API exception messages are not displayed. The client rejects
responses without `sanitization.version == "1.0"`, which also avoids displaying raw
data from an accidentally stale backend.

## Report format 1.0

The JSON document includes:

- report format version, trace reference, event schema version and original source
  fingerprint semantics;
- rule metadata, versions, severities and limitations;
- effective engine configuration (with any recognized sensitive values masked);
- import integrity warnings, all rule findings and bounded field evidence;
- unknown coverage, both full policy configurations/decision runs, counts,
  intervention categories, changed outcomes and reasons;
- ordered event metadata index: event/call references, type, timestamp, tool/status;
- sanitization version, replacement count, reference semantics and limitations.

It excludes raw event `arguments` and `output`, original input text, imported
filename, transient UI selection, top-level selected-policy duplicates and generation
time. Evidence excerpts are analyzed report content, not wholesale payload copies.
There is one finding per matching rule/action; excerpts remain bounded.

Markdown has a human-readable summary plus sections containing the same report
content. Trusted headings/structure are generated by the application. All untrusted
punctuation/control characters are numeric-entity encoded, including Markdown fence,
heading/link/table characters and HTML delimiters. JSON uses ordinary JSON string
escaping and ASCII serialization; it is data, not embeddable HTML. Neither export
renders imported HTML/Markdown as instructions. Do not paste JSON into an unsafe
HTML/script template or assume a downstream editor is safe.

## Exact fingerprints and determinism

`source_sha256` = SHA-256 of original accepted UTF-8 input **bytes**, including CRLF
versus LF and blank lines. It is not a hash of parsed or sanitized events. The
browser preserves valid UTF-8 text/line endings when uploading; BOM remains input
and is rejected by the importer rather than silently discarded.

Canonical report JSON uses Python `json.dumps(sort_keys=True, separators=(",", ":"),
ensure_ascii=True, allow_nan=False)` followed by exactly one LF. Object key order
does not affect serialization; source event/decision arrays retain source order.
This is a project-specific canonical encoding, **not** a claim of RFC 8785/JCS
conformance. `reports.report_sha256` hashes exactly those UTF-8 report text bytes,
including the final LF. The digest is external to the document to avoid self-hashing.
It is not a Markdown digest or a digital signature.

The same accepted input/config produces identical JSON, Markdown, aliases and
report digest; selecting baseline versus strict does not change the reports. A
rule/policy/redaction implementation or version change can change report bytes.
There is no clock, network call, randomness or stored state in report generation.

To verify a downloaded JSON report with the project venv Python:

```sh
python -c "import hashlib,pathlib; print(hashlib.sha256(pathlib.Path('agenttrace-report-EXAMPLE.json').read_bytes()).hexdigest())"
```

Use the actual downloaded filename in place of `EXAMPLE`; compare to the displayed
Report SHA-256. The original source fingerprint can confirm a known file and is
not anonymization: publishing either digest may reveal possession of known inputs.

## Best-effort redaction 1.0

Discovery covers case-insensitive Authorization/Proxy-Authorization/X-API-Key,
Cookie/Set-Cookie headers; nested password/passwd/token/secret/api-key/access-token/
refresh-token/client-secret/private-key/credential fields; Basic/Bearer text; common
credential-shaped prefixes (AWS access IDs, OpenAI-style and GitHub-style tokens);
literal synthetic secret markers; credential assignments in strings; URL credentials;
and private-key BEGIN/END blocks, including unfinished delimiters. Numeric/boolean
values in recognized sensitive fields are also masked. Tests contain synthetic
values only, including key delimiters without real private keys.

Discovery precedes replacement so a recognized value repeated in a secondary field,
tool name, excerpt or metadata is also hidden. Limited URL-quoted/JSON-escaped forms
and Basic credential decoding help correlate common representations. Matching uses
bounded multi-pattern prefixes rather than one full scan per secret per field.

### Opaque references and integrity

Recognized sensitive values receive local ordinal references such as
`[REDACTED:secret-0001]`, not hashes of low-entropy secret values. Sorted-key discovery
and source-order arrays make assignment deterministic. Repeated recognized values
share a reference within one investigation. These are **not** cross-report secret
identifiers or proof that two underlying secrets are equal. Values sharing a
32-character prefix may conservatively share a reference; partial matches of at
least eight characters can mask the rest of a string. Short known values use whole
string/token-boundary matching. False positives can hide innocent suffixes.

Sensitive trace/event/call IDs get separate, unique source-order aliases such as
`[REDACTED:event-0001]`; distinct input IDs cannot collapse. All findings, warnings,
decisions and continuation links use consistent references. The ordered event
metadata index and raw source digest support correlation back to the retained
original file without disclosing the sensitive identifier. Dict-key collisions get
deterministic suffixes rather than silently losing data.

Generated schema keys and controlled rule/decision/version values retain their
meaning even when a credential happens to equal a public word such as `review`.
Those exemptions do not extend into raw payloads. A password whose value is
`review` is still masked; the generated policy decision `review` is not a password
disclosure. Report generation validates event/call/evidence/warning references.

Excerpts and `matched_literal` may be replaced by opaque references. Field names
can also be sanitized. Numeric `start`/`end` offsets refer to the **original**
source field, not the changed-length sanitized payload. A replacement is not a
claim that the underlying raw bytes are in the report. The redaction count is
replacement occurrences, not unique secrets: the API envelope counts the sanitized
analysis, while the report counts its curated content. Different counts are expected.

### Limits — no perfect secrecy

- Unknown secret names, unusual token formats, arbitrary encodings, encryption,
  transformed fragments and fragments shorter than eight characters can evade
  heuristics. Do not treat the absence of redactions as a secrecy guarantee.
- False positives and conservative prefix masking can hide unrelated evidence or
  parts of a description. Recheck the original locally when authorized.
- Raw values necessarily exist in importer/engine request memory and the user's
  selected browser File/text during processing. This is not memory wiping, at-rest
  encryption, access control or anonymization.
- Public source/report digests are integrity aids, not signed attestations. Report
  findings are limited deterministic signatures, not confirmed harmful effects.
- No report predicts subsequent agent behavior. Counterfactual policy replay
  evaluates **recorded actions only**; it never executes them.

## Release checks and browser verification gap

`python scripts/test.py` runs the backend/frontend tests and TypeScript check;
`npm run build` builds the production assets. `python scripts/smoke.py --port 8000`
checks a live built server, all samples, comparison/config, sanitized findings,
report digest, report consistency across both policies and malformed-input rejection.
The existing Linux CI runs these plus a Docker build with network-disabled test
layers and a read-only/no-external-network container smoke test. Installation/image
pulls require network or a prepared cache; tests and runtime require no hosted API.

Automated cases cover repeat/key-order/selected-policy determinism, exact hashes,
source-byte distinctions, all sample policies, missing references, no payload copies,
Markdown/HTML attacks, auth/cookies/private-key/numeric credentials, secondary-field
leaks, truncated excerpts, sensitive identifier collisions, 10,000 recognized
values, download Blob bytes/types, safe filenames and URL cleanup, keyboard evidence
navigation, loading/errors and stale-backend refusal.

During this milestone, `browser_open` for the local app timed out; a subsequent
built-in browser tab inventory was empty. No desktop screenshot, narrow viewport,
real file-picker or real download completion was observed. DOM tests and responsive
CSS are **not** a real-browser visual audit. This gap remains explicit rather than
claiming browser verification from an HTTP response or a mocked anchor click.

Manual acceptance checklist for an available browser (desktop and ~390px wide):
Explore demo; inspect both summaries; switch policy; follow evidence links by
keyboard; open redaction details; import a valid/invalid JSONL file; confirm error
recovery; download both formats and verify bytes/digest; check no horizontal overflow,
visible focus and readable contrast. A screen-reader/contrast audit remains separate.
